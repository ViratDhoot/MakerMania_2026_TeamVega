# 4. Problem Framing

## Problem Statement

Students and young casual players need a fun, portable, screen-free physical multiplayer gaming experience because many casual multiplayer games are either phone-based, board-game based, or lack tactile electronic interaction.

Current framing:

**Brawl Box** aims to create a compact handheld multiplayer console where each player gets a dedicated physical device with controls, display, sound, vibration, and wireless interaction.

---

## How Might We Questions

1. How might we create a physical multiplayer game experience that does not depend on phones?

2. How might we make a low-cost handheld gaming device that feels polished and interactive?

3. How might we use physical controls such as buttons, rotary encoder, sound, and vibration to make the game more engaging than a simple screen-only game?

4. How might we design the same hardware so it can support multiple simple games in the future?

## Selected Concept

The current selected project direction is **Brawl Box** — a compact handheld multiplayer gaming console prototype.

The first planned game is a maze-battle style game where players spawn from different edges of the maze and race toward the center while collecting abilities such as health, speed boost, and bomb-based attacks. Each player uses a separate handheld device with a TFT display, physical buttons, rotary encoder, sound feedback, vibration feedback, and wireless communication.

Brawl Box is being designed as a small expandable handheld console platform rather than only a single game. The same hardware can later support additional simple multiplayer games through firmware updates.

# 6. System Design

## High-Level Description

**Brawl Box** is a 3-device handheld multiplayer gaming system. Each device acts as an individual player console with its own screen, controls, sound output, vibration feedback, and battery power.

The initial game mode is a maze-based battle race. Players start from different edges of the map and try to reach the center while collecting abilities and disrupting opponents. The rotary encoder adds a hardware-first interaction layer for menu control, opponent selection, and bomb targeting.

# 14. Reflection

## What Worked Well?

Week 1:

* Team completed the useless product activity.
* BusyBuds was taken from an idea to a 3D printed product and advertisement.
* We got hands-on exposure to CAD, laser cutting, 3D printing, documentation, and video-based pitching.
* The useless product task helped us think broadly and frame even unusual ideas convincingly.

Week 2 so far:

* Problem discovery started with Google Form responses and informal discussions.
* Multiple ideas were discussed before narrowing down.
* The SCAMPER activity helped compare ideas from different perspectives.
* ESP32 basics were revised through a simple hardware activity.
* The team moved toward a buildable hardware-first project direction.
* Brawl Box helped the team define a clear hardware stack involving ESP32, TFT display, controls, sound, vibration, and enclosure design.

---

## What Failed?

Week 1:

* The first 3D print attempt for BusyBuds needed improvement because the support setup was not planned well.
* Some decisions took time to finalize during team activities.
* Documentation could have been updated more frequently during the activity.

Week 2 so far:

* Some early ideas were too vague or difficult to frame clearly.
* The local-train bag holder idea was dropped because it shifted the load instead of reducing it.
* Some high-impact ideas were too expensive, AI-heavy, or difficult to prototype within the current scope.
* Some project directions were difficult to align on as a team.
* The electronics architecture needed extra discussion because the team is still learning hardware integration.

---

## Key Learnings

Week 1:

* CAD and 3D printing require attention to dimensions, supports, orientation, and printability.
* A product pitch depends not only on the object, but also on framing, storytelling, and presentation.
* The useless product activity helped us explore multiple directions before locking an idea.
* Documentation is easier when progress is recorded continuously.

Week 2 so far:

* A good problem statement needs a clear user, pain point, and use case.
* Not every relatable problem becomes a strong prototype idea.
* Hardware ideas need to be checked for cost, feasibility, mounting, durability, and user value.
* SCAMPER helps in expanding ideas, but the final project still needs deeper validation.
* Even basic ESP32 revision is useful for getting back into the embedded workflow.
* For embedded products, choosing components early affects software, enclosure, cost, and demo feasibility.
* Power architecture, communication, display choice, and physical controls must be planned together.
